## Blocking findings

**P1-1 — oracle / no narrowing — brt-6dn — `scripts/native-check.cpp:143–148`.**
Named AVX vectors are already valid frontend ABI-lowered direct operands.
With `typedef float V __attribute__((vector_size(32)));`, a noinline
`take(int n, V v, ...)` returning `n + (v[7] != 8.f)`, called with
`take(0,(V){1,2,3,4,5,6,7,8},42)`, compiles at `-O0 -mavx` to a call
with named `<8 x float>`. On LLVM18/23, base checked and current plain native
both link and exit 0; head checked linking aborts with
`LLVM ERROR: unmaterialised variadic argument class` / SIGABRT.
A valid callee that reads its variadic int is also rejected. Named 512-bit
vectors similarly link at base/plain and abort at head (not executed).
The table's claim at lines 112–115 that direct wide vectors need more frontend
lowering is false for named AVX operands. Ran `python3 -B "$R/extra-probes.py"`;
`extra.txt`, `tmp/extra/named-avx-{ignored,read}-{18,23}.c/.ll`.

**P1-2 — oracle — brt-yz5 — `scripts/native-check.cpp:104,141`.**
All accepted 65–128-bit integers inherit `__int128`'s special 16-byte stack
alignment. Direct `i65`/`i96` instead occupy two 8-byte-aligned chunks.
The accepted call `take(i32 0, six i64 ones, i65 7)` has 24 passed stack bytes
(one GP spill plus two chunks), but publishes 32. On LLVM23 a valid control
reading the values at overflow offsets 0 and 8 exits 0 checked/plain.
Adding a volatile read at **+24**, the first byte beyond the passed arguments,
incorrectly exits 0 checked; adding another at +32 finally faults 7.
Independent caller assembly stores at offsets 0/8/16.
Ran `python3 -B "$R/ir-class-probes.py"` and
`python3 -B "$R/accepted-classes.py"`; receipts `ir-class.txt`,
`accepted-classes.txt`, inputs `tmp/accepted-classes/i65-{valid,over1,over2}-23.ll`.
This concerns a **direct accepted LLVM type**; the C frontend's `byval align 8`
`_BitInt(65)` control remains correct. LLVM18 plain/checked both return 1 on
the direct-i65 value control; no LLVM18 valid-result claim is made.

**P1-3 — oracle — brt-st3 — `scripts/native-check.cpp:108,143–146`.**
Vector width alone does not determine placement for all accepted LLVM types.
Both native backends stack-pass `<1 x i64>` even with XMM registers free.
The accepted call `take(i32 0, six i64 ones, <1 x i64> <i64 7>)` has 16
passed stack bytes, but publishes 8. A callee using `llvm.va_start` and reading
the passed fields at overflow offsets 0 and 8 exits 0 plain, but falsely faults
7 checked on LLVM18/23. This is a verdict mismatch on the **identical module**,
not a claim that C `__m64` is stack-class; its frontend coercion is different.
Ran the same two commands as P1-2; `accepted-classes.txt`,
`tmp/accepted-classes/v1i64-valid-{18,23}.ll` and
`tmp/ir-class/_1_x_i64_-{18,23}.s`. The advertised table must match every accepted
operand representation, including backend placement after legalization.
